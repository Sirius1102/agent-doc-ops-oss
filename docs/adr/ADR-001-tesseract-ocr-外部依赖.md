# ADR-001 · 引入 Tesseract 作为 `ocr` 子命令的外部 OCR 引擎

- 状态：已接受（2026-10-05，机主裁定"装"并放行命令面；监工侧方案与验收）
- 修订：v1.6.0（2026-10-06）§四「何时重新评估」触发项 ③ 追加一条**带日期的本机事实订正**（任务书 H R1-c ／《方案》Q-04=②）；只订正事实，**不重跑对照、不改本 ADR 的决策**
- 关联：任务书 G；选型证据 `OCR选型报告-2026-10-04.md`（C1/C3 本机第一手实测）；装机记录 迭代日志 C3 条（2026-10-05）

## 一、背景

装置自 v1.0.0 起的承重约束是"**只依赖 `@deepseek-ai/libreoffice-kit` + Node 标准库**"（总览第三节技术路径），刻意不 import kit 的 JS API、不引 python/pandoc——每多一个外部面就多一个"换机器/升级即碎"的漂移源。但 C1/C3 实测确立了两个事实：① 有源文件时文本层直提（`to txt/csv`）永远优先，**不需要 OCR**；② 只有渲染图/扫描页时，OCR 是唯一取字路线，而 WinRT 内置引擎对**表格页的单元格级匹配只有 74.4%**（真 `.xls` 派生件 180 格逐格比对），表格取数场景不达标。机主在 C3 门槛判定成立后裁定：装 Tesseract、给装置加 `ocr` 子命令。

## 二、候选（全部带本机第一手数字，不用官网宣传值）

- **A. 只走 kit，不装引擎（被否）**：对"只有图"的页无解；正文页场景文本层已覆盖，但表格/扫描页缺口真实存在（C1：表格页 WinRT 74.4%）。
- **B. WinRT 桥（零依赖，曾为唯一在位路线）**：正文页 precision 0.9779／真召回 0.9600／92 ms/页，空白对照 0 幻影——但**表格页逐格 74.4%（134/180）不达标**，且质量随 Windows 更新漂移、不可钉版。保留为"没装 Tesseract 的机器上的能力边界"（`ocr` 命令不回退到它——降级必须可诊断，见后果）。
- **C. Tesseract 原生 CLI（UB-Mannheim 构建，本选）**：本机 5.4.0.20240606 实测——正文页 precision 0.9850／真召回 0.9843；**表格页逐格 79.44%（chi_sim best）/80.00%（fast）> 74.4% 门槛**；代价：约 7.7–10.5 倍慢（968.8/705.4 ms/页 vs 92，计时口径不同已在选型报告注明）；blank 对照 2/2 零行。
- **D. Python 系 OCR（RapidOCR/PaddleOCR，被否）**：本机**没有 python**（只有 WindowsApps 占位符，会假报"未找到"），引入 Python 运行时的 blast radius 远大于一个自带 tessdata 的单目录 exe；且其质量上限（PP-OCR 系）Tesseract 路线已够过门槛。

## 三、决策

给 `dockit.js` 加 `ocr` 子命令，调本机 Tesseract 原生 CLI（spawnSync，与 kit 同为子进程调用形态）；路径/语言包目录/默认语言进配置区常量（同一字面量全仓一次），支持 `DOCKIT_TESSERACT`／`DOCKIT_TESSDATA` 环境变量覆盖并自报实际解析路径；**缺引擎时降级为 `unavailable`＋指路＋退码 1**，`doctor` 加 Tesseract 哨兵（不在位报 WARN 不 FAIL），相关判据在不装 Tesseract 的机器上逐条 SKIP——**外人克隆必须依旧全绿**。不回退到 WinRT（能力边界写进文档，不混进命令面）。**【2026-10-05 v1.5.0 收紧】**"自报实际解析路径"还不够——路径对、路径**里有什么**报错了同样是骗人：`ocr` 现另报 `langCount`／`langs`，且**按本次真用的那个目录**跑 `--list-langs`（此前恒按默认／env 目录跑，于是用 `--tessdata-dir` 换包时，同一条 JSON 里目录名跟着变、语言清单却还在说默认目录那套）。

## 四、后果

- **换来**：表格/扫描页取字达标（逐格 79.44%/80.00% vs 74.4%）；引擎版本可钉（5.4.0.20240606）、行为不随 OS 更新漂移；一条命令＋JSON 自曝（backend/tessdataDir/langPack/逐页行数字数/非白像素占比/耗时）。
- **付出**：**装置不再是"零第三方依赖"**——新增一个系统级外部程序依赖（Tesseract 5.4.0.20240606，装在 `C:\Program Files\Tesseract-OCR\`，另有语言包目录可由 `DOCKIT_TESSDATA` 指向仓内 `_out/tessdata-*`）；换机器/新克隆没装 Tesseract 时 `ocr` 不可用（必须可诊断：`unavailable`＋指路，doctor WARN，判据 SKIP 逐条点名）；`ocr` 慢（≈0.7–1.0 s/页），批量按串行算。
- **何时重新评估**：① Tesseract 与 kit 任一方升版破坏 `ocr` 或转换面（重跑全阶梯）；② 出现"必须更高字准"的交付要求（重跑 C3 同口径对照，看 RapidOCR 等 ONNX 路线能否顶过 79.44%/80.00%）；③ 本机引入 Python 运行时（D 候选重新入圈）——**【2026-10-06 订正，任务书 H R1-c／机主 2026-10-05 裁 Q-04=②】本条按字面已经成立：这台机器上确实有一个可用的 Python**，实测 `%LOCALAPPDATA%\Python\bin\python.exe` 回 `Python 3.14.3`，文件 605,016 B、日期 2026-03-16（与本仓无关，装机早于 ADR-001 自己）。但**裸 `python` 与 `python3` 都被 WindowsApps 的执行别名挡住**，实测退码 **49** ＋ 那句"Python was not found; … install from the Microsoft Store"——本仓 2026-10-05 成文时写的"本机没有 python"是**按裸命令名的口径**说的，严格讲不准确，正确表述是"没有可直接调用的 `python`，但有一个必须写绝对路径才用得上的 CPython 3.14.3"。**机主裁定：这不算本轮引入的外部依赖，D 候选不重新入圈、维持不重跑 C3 对照**（执行者不得自行把它当"触发项已满足"去起一轮对照，也不得把上面这些数字当"已重跑"的证据）；④ WinRT 质量随 OS 更新漂移到表格可达标（B 候选重新入圈，省掉外部依赖）；⑤ 🔴 **生僻字／大写数字／人名用字进入交付范围**——2026-10-05 监工侧交叉对账（`_probe/cn.pdf` 走 `chi_sim`）实测出**"表格逐格达标 ≠ 罕见字达标"**：同一页上常用词（文档／装置／取证／专用／汉字／串／对照串／壹／肆／零）逐字对得上，而四个形近的大写数字**全被换掉**（柒→染、捌→提、贰→起、叁→参）。⇒ 一旦交付要求覆盖这一类字，C 候选的质量前提就不成立，重跑对照时**要专门测汉字混淆面，不许再拿表格那 79.44%/80.00% 当"中文能读"的证据**（那是本 ADR 自己犯过的以偏概全，记下以免重犯）。
